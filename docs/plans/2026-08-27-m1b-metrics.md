# M1b — Metrics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development`.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn a run directory into versioned metrics that survive a controller comparison,
including under oversaturation where the naive versions of those numbers invert.

**Architecture:** A new Zone A package `src/cadence/metrics/` reads a completed run directory
and writes a `metrics/` partition back into it. It never imports `simulation/sumo/`, never
touches SUMO, and never reads `ground_truth/`. Three writer changes land on the M1a side
first, because a run made without them cannot be scored later without being re-simulated,
and the simulator's failure behaviour is pinned before anything is measured at all.

**Tech Stack:** Python 3.12, polars, pydantic, typer, pytest, hypothesis.

**Spec:** `docs/specs/2026-08-27-m1b-metrics.md` — read it. Every task argues from it, and
where this plan and the spec disagree, the spec is right.

## Why this plan contains no function bodies

M1a's plan carried complete implementations for all nine tasks, written before any of them
existed. Nine commits were then spent repairing it as the shipped tree diverged: a type moved
module, a property was removed, a return type changed from list to tuple — and each
divergence invalidated code already written into later tasks. Fourteen further defects were
caught in the last three briefs only because they were re-checked against the tree
immediately before dispatch.

So this plan specifies **exact signatures, exact test intent, and the reasoning a wrong
implementation would violate** — and stops there. Bodies are written against the tree that
exists at dispatch time, not against the tree this document imagines.

Two consequences for whoever executes it. Each task's brief is generated from the tree when
that task is dispatched, never earlier. And an implementer who finds a signature here that
does not match the tree has found a plan defect: report it, do not silently adapt.

The format is not a cure. This plan's first draft asserted that a test "does not exist
today" which had in fact been committed by an earlier session — a negative claimed without
grepping for it. Signatures were checked against the tree; an absence was not. Check both.

## Global Constraints

Copied from `CLAUDE.md` and the spec. Every task's requirements include these.

- `mypy --strict` passes. `ruff` with `E,F,W,I,N,UP,B,SIM,TID,ANN,RUF`, line length 100.
- Units are part of every name: `length_m`, `time_s`, `queue_length_m`, `min_gap_m`,
  `occupancy_ratio` (0-1). Bare `length`, `speed`, `time`, `queue` are rejected.
- No `traci` / `libsumo` / `sumolib` import outside `simulation/sumo/`.
- **No module in `src/cadence/metrics/` may contain the string `ground_truth`** (`ST-D30`).
- Determinism: no wall-clock, no unseeded randomness, no dict-ordering dependence.
- Every numeric constant is a named constant with a provenance comment.
- Comments are rare: PROVENANCE, GOTCHA, DECISION or CONTRACT only, and **not a tagging
  syntax** — do not prefix a comment with `PROVENANCE:` or `DECISION:`. `GOTCHA:` is the one
  exception. No `Args:` / `Returns:` blocks.
- If a claim can be a test, it must be a test (`CLAUDE.md` §6).
- The gate is `make check`. It is green at 261 passed, 1 xfailed.

```
src/cadence/simulation/                 MODIFIED — Tasks 1 and 3
├── topology.py            + VehicleTypeInfo, NetworkTopology.vehicle_types
├── state.py               + Traversal.from_lane_id
├── ground_truth.py        + LaneTurnVehicleCount
├── artifacts.py           + topology/vehicle_type.parquet, ground_truth/lane_turn_vehicle.parquet
├── manifest.py            + COMPARABILITY_FIELDS

    ├── topology_reader.py + read vehicle types

tools/build_s0_scenario.py              parameterised; writes a third scenario
tests/test_architecture.py              + the metrics package fences
```

**Why `loader.py` exists as its own module.** `ST-D30` is a rule about which partitions the
package reads. If every metric module opens its own Parquet path, the rule is enforced only
by the string test. Concentrating every path in one module makes the boundary a thing you can
read, and the string test becomes the backstop rather than the whole mechanism.

### Task 2: The oversaturated fixture
`status: done`
**Files:** `tools/build_s0_scenario.py`, `scenarios/s0_turning_oversaturated/v1/`,
`tests/test_s0_scenario.py`

**Produces:** a third scenario directory, generated byte-reproducibly by the same tool.

**Interfaces:** none consumed. Later tasks read the scenario by path.

Everything measured in the spec's §3, §5 and §10.2 came from a variant that does not exist in
the repository. It exists first because every later task's tests need it.

Three properties are load-bearing and each was established by measurement (spec §10.2):

1. **The demand keeps its asymmetry.** Build it by *scaling* `TURNING_PERIODS_S`, not by
   flattening every flow to one period. Flattening cuts §8's mutation-detection power from
   detection and destroys the property `build_s0_scenario.py`'s own comment says
   the asymmetric demand exists for.
2. **`time_to_teleport_s` is below the horizon.** Inheriting 300.0 against a 180 s horizon
   makes a teleport structurally impossible, which would ship every teleport metric untested.
   30.0 produces 12.
3. **The id keeps the network's defining property**: `s0_turning_oversaturated`, not
   `s0_oversaturated`.

`DIRECTION` §4 holds that regimes are parameterised variants rather than separate scenarios
(`TC-D01`), and `ScenarioConfig` has no regime dimension — so a new id is the only mechanism
available. Note that in the scenario's `description`; do not silently let a regime become a
scenario.

- [ ] **Step 1** — Parameterise the generator. It currently hardcodes `SCENARIO_ROOT`,
      `TURNING_SCENARIO_ROOT`, `DEPART_END_S` and `TURNING_PERIODS_S` as module constants.
      Extract what varies per scenario; leave what does not.
- [ ] **Step 2** — Extend the existing byte-reproducibility test.
      `test_the_generator_reproduces_the_committed_scenarios_byte_for_byte`
      (`tests/test_s0_scenario.py:167`) already runs the generator against the two committed
      scenarios; it gains the third. The plan's first draft claimed this test did not exist.
      It does — check before you write.
- [ ] **Step 3** — Generate the scenario. Pick the period scale so the run is clearly
      oversaturated within a horizon short enough to keep tests fast. The spec's measurements
      used every flow at 3.0 s over 180 s; a *scaled* asymmetric equivalent will not
      reproduce those exact counts, so **measure the new fixture and report its numbers** —
      they become the values later tasks assert.
- [ ] **Step 4** — Verify the three properties: it does not drain before the horizon, it
      produces teleports, and the demand keeps the distinctness it actually has. **Not "the
      twelve volumes are mutually distinct" — they are not, and scaling cannot make them so.**
      `TURNING_PERIODS_S` has 10 distinct values across 12 movements: 12.0 and 20.0 each
      appear twice, across approaches, so the derived counts are 10 distinct of 12 as well.
      The invariant the generator's own comment states is per-approach distinctness (3 of 3
      for all four approaches) plus distinct total arrival rates per approach. Assert that.
- [ ] **Step 5** — `make check`, commit.

**Report:** the fixture's measured completed / unfinished / never-inserted counts, teleport
count, and drain behaviour. Later tasks assert against these, so they must come from your run.

### Task 4: The reconciliation test (`ST-D31`)
`status: done`
**Files:** `tests/test_cli.py` or a new `tests/simulation/sumo/test_reconciliation.py`

**Consumes:** everything Task 3 produces.

**Run this on `s0_turning`, not the oversaturated fixture.** Measured: the permutation is
caught on 7 of 16 traversed pairs there, against 3 of 16 on the oversaturated fixture.
Detection is strongest where the network is *not* saturating: congestion inflates
`distinct_veh` relative to traversals, and slack is what the one-sided inequality has to
spend before it can fail.

The assertion, per spec §8:

```
for every (lane L, edge E):   distinct_veh(L, E)  >=  traversals(L → E)
```

Every vehicle that crossed from L to E must have stood on L intending E. The excess is
vehicles that changed lane before the stop line.

- [ ] **Step 1** — write the test; verify it passes on the tree as-is (baseline violations
      are zero — measured).
- [ ] **Step 2** — **verify it by mutation.** Permute each vehicle's next edge among the
      movements *its own lane serves*, run, and confirm the test fails. A mutation that
      crosses approaches is not a valid check — the existing edge-reachability assertion
      catches those, so it proves nothing about this one.
- [ ] **Step 3** — restore the source, confirm green, commit. **If the mutation does not
      make the test fail, the design is wrong: report it and stop.**

- [ ] **Step 1** — `RunDirectory`. The population filter for completed trips is
      `arrival >= 0`, declared explicitly. **Not `vaporized`** — not every unfinished row
      carries `vaporized="end"`, measured on both fixtures.
      `manifest()` returns `RunManifest` from `cadence.simulation.manifest`. That import is
      legal under the fence: the rule is *no import from `simulation/sumo/`*, checked on direct

- [ ] **Step 2** — the architecture tests: no module under `metrics/` contains the string
      `ground_truth`, and none imports from `simulation/sumo/`. Follow the exact-set pattern
      already in `tests/test_architecture.py`.
- [ ] **Step 3** — `account()`, and the identity tests. Two sources, two scopes — keep them
      apart:
      - **every step**, from `state/network.parquet` alone:
        `departed_total_veh = arrived_total_veh + active_veh`. Verified that way on the fixture,
        and a horizon-only check would miss a mid-run divergence that closes again.

### Task 7: Trip metrics (`ST-D27`)
`status: todo`
**Files:** `src/cadence/metrics/trip.py`, tests

**Consumes:** `RunDirectory`, `MetricDefinition`, `Population`.

The censoring rule is the whole content of this task. An unfinished trip's `duration` is not
its travel time — it is how long the clock ran. On the spec's fixture, completed trips
averaged 78.04 s and unfinished 84.44 s — 8% apart, while the unfinished carried 67% more
waiting. Pooling them is not a travel-time statistic and can still reward the controller that
stranded more.

*Those figures are provisional: they came from the spec's flattened demand, and Task 2 builds
a scaled asymmetric one. Re-measure against Task 2's fixture before any of them enters a
test. The censoring argument does not depend on the numbers; the tests do.*

- [ ] **Step 1** — metrics over `COMPLETED_TRIPS`: travel time, waiting, time loss, depart
      delay. Each with a declaration naming its population.
- [ ] **Step 2** — the unfinished population reported **separately**, and its duration named
      so no reader mistakes it for travel time. The name carries the censoring
      (`time_in_network_at_horizon_s`, not `travel_time_s`).
- [ ] **Step 3** — the structural test: no metric declares a population spanning the
      censoring boundary. This is asserted from the declarations, not from the arithmetic —
      it stays true for metrics nobody has written yet.
- [ ] **Step 4** — `make check`, commit.

### Task 8: Queue, network and teleport metrics, and the agreement tests
`status: todo`
**Files:** `src/cadence/metrics/{queue,network,teleport}.py`, tests

`queue_length_m = halting_count_veh × (length_m + min_gap_m)` — back-of-queue distance, on
Task 3's fleet record.

**Selecting the vehicle type is a trap, and no fixture in this repository can catch you.**
`topology/vehicle_type.parquet` holds seven rows: the demand's `car` plus six `DEFAULT_*`
types SUMO registers on its own. Three of them — `car`, `DEFAULT_VEHTYPE`,
`DEFAULT_TAXITYPE` — have identical length and gap, 5.0 m and 2.5 m. **Pick the wrong one of
those three and every number you produce is correct on every fixture that exists.** Assert
the selection structurally, against the types actually used —
`selected == set(tripinfo["vType"])`, which reads `{"car"}` on both fixtures — never by
checking that the resulting metres look right. (`DEFAULT_BIKETYPE` sorts first at 2.1 m, so
"take row 0" *would* be caught. That is the only wrong answer that would be.)

`tripinfo` covers only vehicles that departed, so a run where nothing departs cannot answer
which types were in use. That belongs in the metric's `limitations`. Spec §5.3 measured the alternative reporting a full 189.6 m lane as
125 m; do not reintroduce it. The mixed-fleet weighting is a `limitations` entry until a
mixed-fleet scenario exists.

`ST-D28` governs every aggregation here. `waiting_total_now_s` already carries seconds, so it
is used for instantaneous and peak statistics and **never integrated**. `halting_count_veh`
does not, so `Σ halting_count_veh · Δt` is correct and is the total-delay metric.

Network metrics report completion on **both** denominators — over departed and over due —
because under oversaturation they are different claims and the gap is the never-inserted
bucket (spec §3.3).

Teleport is incidence, not an outcome bucket (spec §3.2): incidences, distinct vehicles
affected, and completion rate of affected versus unaffected. On the spec's teleporting
variant, 8 of 12 affected completed (67%) against 158 of 333 unaffected (47%) — *provisional,
re-measure against Task 2's fixture. The direction is the point: affected vehicles complete
at a higher rate, because being teleported is what released them.*

- [ ] **Step 1** — the three modules, each metric declared beside its function.
- [ ] **Step 2** — **the agreement tests.** This is the important step in the plan. Every
      finding in the spec's §5 came from measuring one quantity two independent ways; nothing
      else in the test suite would have found any of them. A unit test against a hand-built
      frame is written by whoever wrote the metric, so it separates "runs" from "crashes",
      never "runs" from "correct". Implement all four of spec §10.1:

      - `Σ_t halting_count_veh · Δt` ≈ `Σ tripinfo waitingTime` (1.0% apart on the spec's
        fixture; measure the gap on Task 2's and use that)
      - `tripinfo` rows with `arrival >= 0` == `arrived_total_veh` at the horizon
      - `tripinfo` row count == `departed_total_veh` at the horizon
      - per-movement traversal totals ≈ `tripinfo` route counts

      Choose and justify the tolerance for the two approximate ones from what you measure,
      and state the measured gap in the test's message so a future failure shows the drift.
- [ ] **Step 3** — `make check`, commit.

### Task 10: `cadence verify-run` (`ST-D33`)
`status: todo`
**Files:** `src/cadence/simulation/manifest.py`, `src/cadence/cli.py`, tests

**Produces:**

```python
# manifest.py — NEW sets. Together with NON_REPRODUCIBLE_FIELDS they partition
# RunManifest exactly, so a field added later cannot fall into none of them.
COMPARABILITY_FIELDS = frozenset({          # must agree, or the runs are not comparable
    "scenario_id", "scenario_version",
    "network_sha256", "demand_sha256", "config_sha256",
    "begin_s", "end_s", "step_length_s", "time_to_teleport_s",
    "cadence_commit", "cadence_version", "python_version",
    "platform_tag", "sumo_version", "binding",
})
INTENDED_DIFFERENCE_FIELDS = frozenset({    # reported, never compared for equality
    "controller_id", "controller_version", "seed",
})
OUTCOME_FIELDS = frozenset({                # results of the run, not inputs to it
    "terminal_time_s", "step_count", "unmatched_traversal_count", "termination_reason",
})
DIRTINESS_FIELDS = frozenset({              # the refusal gate, not a comparison
    "cadence_dirty", "cadence_dirty_digest",
})
```

`RunManifest` has 26 fields; these four sets plus `NON_REPRODUCIBLE_FIELDS` cover
15 + 3 + 4 + 2 + 2 = 26. **The plan's first draft asserted a completeness test over two sets
covering 15 of them — a test that could not have passed.** The partition is the fix, and it
is worth more than the arithmetic: it forces every future manifest field to be classified as
input, intended difference, outcome, dirtiness, or noise.

**Do not reuse `reproducible_fields()`.** It answers "are these the same run?" and excludes
only the two timestamps, so it still carries `controller_id`, `controller_version`, `seed`,
and four run outcomes. Every one of those differs by construction in a controller comparison,
so reusing it would make `verify-run` refuse M3's fixed-time-versus-actuated comparison — the
case it exists to bless.

`controller_id`, `controller_version` and `seed` are **reported as the intended differences**,
not compared for equality. `verify-run` says which kind of comparison it is looking at: two
runs differing in nothing there is a reproducibility check, not a controller comparison.

- [ ] **Step 1** — the four sets, and a test that all five **partition**
