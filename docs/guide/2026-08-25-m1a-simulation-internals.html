กลไกของ simulation/

14 ไฟล์ 1,704 บรรทัด ที่แปลงการจำลอง SUMO เป็นข้อมูลที่ไม่รู้จัก SUMO — ไล่ทีละกลไก พร้อมกับดักที่เจอมาแล้วจริง

01

สองวงแหวน และทิศทางของการพึ่งพา

โฟลเดอร์นี้แบ่งเป็นสองชั้น ชั้นในรู้จัก SUMO ชั้นนอกไม่รู้จักเลย และการพึ่งพาวิ่งทางเดียวเสมอ: ชั้นในเรียกใช้ชนิดข้อมูลของชั้นนอก แต่ชั้นนอกไม่เคยเรียกชั้นใน

simulation/sumo/ — ชั้นใน

แตะ traci / libsumo / sumolib ได้ที่เดียว มีเทสต์บังคับ

validation.pyตรวจถนนก่อนรัน

simulation/ — ชั้นนอก

02

ตอนเปิด — อ่านรูปร่างถนนครั้งเดียว

read_topology() ถาม SUMO ครั้งเดียวตอนเริ่ม แล้วสร้างตารางสี่ชุดที่คงที่ไปตลอดการรัน ทุกอย่างเป็น MappingProxyType คือ dict ที่แก้ไม่ได้

ตารางเก็บอะไรถาม SUMO ว่า
lanesความยาว ความเร็วจำกัด อยู่ edge ไหน เลนที่เท่าไรlane.getIDList / getLength / getMaxSpeed
connectionsเลนไหนต่อไปเลนไหน ผ่านแยกด้วยทิศทางอะไรtrafficlight.getControlledLinks
movementsconnection ที่เป็นการเลี้ยวเดียวกัน จับกลุ่มไว้คำนวณจาก connections
phasesโปรแกรมไฟ: แต่ละ phase นานเท่าไร สัญญาณอะไรบ้างtrafficlight.getAllProgramLogics

กับดักสามอันในฟังก์ชันเดียว

เลนภายใน

SUMO สร้างเลนสมมติข้างในแยกเอง ชื่อขึ้นต้นด้วย : มันเป็นทางผ่าน ไม่ใช่ถนนจริง — กรองทิ้งตั้งแต่ตรงนี้ ไม่งั้นทุกการนับรถจะเกินจริง

เลขเลน

SUMO ไม่มี getter สำหรับ "นี่คือเลนที่เท่าไรของ edge" ต้องแยกจากชื่อเอง "e1_0".rpartition("_") ซึ่งเป็นวิธีประกอบชื่อที่ SUMO ประกาศไว้ในเอกสาร ไม่ใช่การเดา

โปรแกรมไฟ

getAllProgramLogics คืนทุกโปรแกรมที่นิยามไว้ ไม่ใช่โปรแกรมที่กำลังวิ่ง ถ้าแยกหนึ่งมีทั้งโปรแกรม actuated และ static สำรอง หยิบตัวแรกมาอาจได้ตัวที่ไม่เคยทำงาน — ต้องเทียบกับ getProgram() ก่อน

ทิศทางการเลี้ยว (s t T l r L R) อ่านมาจาก lane.getLinks ของ SUMO เอง ไม่คำนวณจากพิกัดใหม่ เพื่อไม่ให้โปรเจกต์มีความเห็นที่สองว่าอะไรคือการเลี้ยวซ้าย

03

ทุกวินาที — และทำไมลำดับถึงสำคัญ

connection.step() ทำห้าอย่างเรียงกัน และ สองอันตรงกลางสลับกันไม่ได้

  • binding.simulationStep()สั่ง SUMO เดินไปหนึ่งวินาที
  • เก็บ eventsออกตัว · ถึงที่หมาย · teleport เริ่ม/จบ · ชน — ทั้งหมดคือรายการรถของ step ที่เพิ่งผ่านไป
  • อ่าน held_lane ของรถที่กำลัง teleportต้องอ่านก่อน เพราะ getLaneID() คืนสตริงว่างสำหรับรถที่กำลังถูกย้าย เลนที่มันจากมาเหลืออยู่แค่ในหน่วยความจำของ detector เท่านั้น
  • forget(รถที่ teleport)ต้องลบก่อน observe() ไม่งั้น detector จะเทียบเลนขาเข้าที่มันจำไว้ กับเลนปลายทางที่รถไม่เคยขับไปถึง แล้วสร้างการข้ามแยกปลอมขึ้นมา
  • observe() แล้ว extract()ตรวจว่าใครข้ามแยกไปแล้วบ้าง จากนั้นประกอบภาพนิ่งของวินาทีนี้
ทำไมสำคัญ

บน fixture ปัจจุบันมี teleport ศูนย์ครั้ง ลำดับผิดก็ยังผ่านเทสต์ทุกตัว เทสต์ที่ปักลำดับนี้ไว้ต้องลดเกณฑ์ time_to_teleport_s ลงจนเกิด teleport จริง 35 ครั้งถึงจะจับได้ — และ regime C กับ D ที่โปรเจกต์นี้มีไว้ศึกษาโดยเฉพาะ คือที่ที่มันเกิดตลอดเวลา

04

StateExtractor — ประกอบภาพนิ่ง

ถาม SUMO หนึ่งครั้งต่อหนึ่งปริมาณต่อหนึ่งเลน แล้วยัดใส่ LaneState ที่แก้ไม่ได้ ตรงไปตรงมา — แต่มีสองอย่างที่ไม่ตรงไปตรงมา

ยอดสะสมที่ SUMO ไม่ได้เก็บให้

getDepartedNumber() ฟังดูเหมือนยอดสะสม แต่ไม่ใช่ — มันรายงานเฉพาะ step ที่เพิ่งผ่าน

# วัดจริงที่ t=120 หลังมีรถออกตัวไปแล้วเกินร้อยคัน
simulation.getDepartedNumber()   → 0
simulation.getLoadedNumber()     → 0

เลยต้องนับเองจากสาย event ทุก step: departed_total_veh, arrived_total_veh, teleport_total_veh

เรียก SUMO ครั้งเดียวต่อแยก ไม่ใช่ครั้งเดียวต่อ connection

สัญญาณของทั้งแยกมาเป็นสตริงเดียว เช่น "GGrrGGrr" หนึ่งตัวอักษรต่อหนึ่ง connection ที่ควบคุม โค้ดจึงจัดกลุ่ม connection ตามแยกก่อนวนลูป แล้วเรียก getRedYellowGreenState ครั้งเดียว จากนั้นถอดรหัสด้วย link_index ของแต่ละ connection

แยกที่มี 16 connection จึงเสียการเรียก 1 ครั้ง ไม่ใช่ 16 ครั้ง

สัญญาณของ movement เรียงตรงตำแหน่ง

MovementState.signals เรียงตรงกับ topology.movements[id].connection_ids ตำแหน่งต่อตำแหน่ง ตัวควบคุมจึงถามได้ว่า connection ไหนกำลังแสดงสัญญาณอะไร ไม่ใช่แค่ มีอันไหนเขียวบ้างไหม

05

TraversalDetector — อัลกอริทึมที่น่าสนใจที่สุดในโฟลเดอร์นี้

โจทย์: รู้ได้ยังไงว่ารถคันหนึ่งข้ามแยกไปแล้ว และข้ามด้วยการเลี้ยวแบบไหน SUMO ไม่บอก มันบอกแค่ว่าตอนนี้รถอยู่เลนไหน

วิธีคือจำเลนล่าสุดของรถทุกคันไว้ใน dict เดียว (_last_lane) แล้วทุก step เอาเลนปัจจุบันมาเทียบ ถ้าเปลี่ยน ให้ผ่านด่านห้าด่านนี้

เลนเดิม ไม่เปลี่ยน ข้าม ไม่มีอะไรเกิดขึ้น
เลนใหม่ขึ้นต้นด้วย : รถอยู่กลางแยก — ไม่อัปเดตความจำ คงเลนขาเข้าไว้ก่อน เพราะรถเกือบทุกคันถูกเห็นตอนอยู่บนเลนภายใน ถ้าเทียบกับเลนก่อนหน้าทันทีจะแทบไม่มีการข้ามแยกไหนถูกตรวจเจอเลย
เลนเดิมไม่ใช่เลนขาเข้า ไม่เกี่ยวกับแยกนี้ อัปเดตความจำแล้วจบ
edge ใหม่ = edge เดิม แค่เปลี่ยนเลนบนถนนเส้นเดิม ไม่ใช่การข้ามแยก — บน fixture เกิด 121 ครั้ง
หา movement ไม่เจอ นับใส่ unmatched_count — ไม่เงียบ การนับขาดที่ M8 กับทางออกหลายเลนจะดูเหมือนความต้องการเดินทางน้อย แทนที่จะดูเหมือนบั๊ก
ผ่านทุกด่าน บันทึก Traversal — เวลา · รถ · movement · connection

คีย์ที่ใช้ระบุการข้ามแยก เลือกจากการวัด ไม่ใช่จากการเถียง

รถ 315 คันวิ่งครบรอบ คำตอบที่ถูกต้องจึงต้องได้ 315

ใช้อะไรเป็นคีย์ได้เท่าไรพลาดตรงไหน
เลนภายในที่ผ่าน322รถที่เปลี่ยนเลนกลางแยกถูกนับสองครั้ง
คู่ (เลนเข้า, เลนออก)306รถคันเดียวกันหายไปเลย เพราะออกที่เลนที่คู่นั้นไม่ได้ระบุไว้
(เลนเข้า, edge ออก)315ถูกทั้งสองกรณี — และหนึ่งเลนต่อได้ไม่เกินหนึ่ง connection ต่อหนึ่ง edge จึงไม่ซ้ำด้วย
กฎของเลข

ตัวเลขทุกตัวที่ assert ในเทสต์มาจากการรันจริง ไม่เคยมาจากการเดา เมื่อตัวเลขที่วัดได้ขัดกับโค้ด แปลว่าโค้ดผิด ไม่ใช่แก้ตัวเลขให้ตรงกับโค้ด กฎนี้คือเหตุผลที่จับเรื่องคีย์ได้ก่อนจะมีอะไรสร้างทับมัน

06

GroundTruthReader — ตารางที่โกงได้ถ้าเอาไปใช้ผิด

ตอบคำถามที่เซนเซอร์จริงตอบไม่ได้: รถบนเลนนี้ คันไหนตั้งใจจะไป edge ไหนต่อ อ่านจากเส้นทางที่รถถืออยู่

route = vehicle.getRoute(vehicle_id)      # cache ไว้ ไม่ถามซ้ำทุก step
index = vehicle.getRouteIndex(vehicle_id)
if 0 <= index + 1 < len(route):
    key = (lane_id, route[index + 1])     # edge ถัดไป = คำตอบ
else:
    tally = residual[lane_id]             # อยู่ edge สุดท้ายแล้ว ไม่มีถัดไป

route ถูก cache เพราะมันไม่เปลี่ยน (ตราบใดที่ไม่มีการ reroute) และการถามทุก step แพงขึ้นราวเท่าตัวต่อคัน — --device.rerouting.probability 0 ถูกตรึงไว้ใน command เพื่อให้เงื่อนไขนี้เป็นจริงเชิงกลไก ไม่ใช่แค่เขียนไว้ในคอมเมนต์

แถว residual — null คือข้อมูล ไม่ใช่ค่าว่าง

รถที่อยู่บน edge สุดท้ายของเส้นทางไม่มี "edge ถัดไป" แต่มันก็ยังกินที่บนเลนอยู่ดี ถ้าทิ้งไป ผลรวมต่อเลนจะไม่ตรงกับจำนวนรถจริง จึงมีหนึ่งแถวต่อหนึ่งเลนที่ next_edge_id = null เขียนทุกเลนแม้ค่าเป็นศูนย์

นั่นทำให้ตรวจสอบได้ว่า ผลรวมทุกแถวของเลน = LaneState.vehicle_count_veh ซึ่งเป็นเทสต์จริงที่รันอยู่

ทำไมจำนวนรถที่หยุดถึงไม่ตรงกับของ LaneState

สี่เหตุผล และการตั้งเกณฑ์ความเร็วให้ตรงกับ SUMO แก้ได้แค่ข้อแรก:

#สาเหตุ
1เกณฑ์ของ SUMO อยู่ข้างในตัวมัน เปลี่ยนข้ามเวอร์ชันได้ ของเราอยู่ในซอร์ส
2SUMO เฉลี่ยตลอด step ลูปนี้อ่านความเร็ว ณ ปลาย step
3SUMO ใช้การครองเลนของ step ที่แล้ว ลูปนี้ใช้ getLaneID() ณ ปลาย step
4รถบน edge สุดท้ายไม่มีแถวในตารางนี้ แต่ SUMO ยังนับว่าหยุด — ไม่มีเกณฑ์ไหนแก้ได้ ต้องใช้แถว residual
07

RunRecorder — พักไว้ก่อน เขียนทีเดียว

ทุก step แค่ต่อแถวใส่ list ในหน่วยความจำ พอจบรันถึงเขียนลง Parquet ทีเดียว หนึ่งรอบมีขนาดไม่กี่ร้อยกิโลไบต์ การทยอยเขียนจึงไม่ได้อะไร แต่แลกมาด้วยความเสี่ยงได้ไฟล์ครึ่ง ๆ กลาง ๆ

ทุกตารางประกาศ schema ของตัวเอง

ถ้าไม่ประกาศ ตารางที่ไม่มีแถวเลยจะกลายเป็นไฟล์ที่ไม่มีคอลัมน์ แล้วโค้ดปลายทางที่ select คอลัมน์จะพังทันที — รอบการรันที่เงียบที่สุดจะกลายเป็นรอบเดียวที่อ่านไม่ได้

แปลง dataclass เป็นแถว

if not dataclasses.is_dataclass(record):
    raise TypeError(...)
return {f.name: _as_value(getattr(record, f.name))
        for f in dataclasses.fields(record)}

ใช้ dataclasses.fields() ไม่ใช่ __slots__ เพราะ slotted dataclass ที่มีคลาสแม่จะเก็บเฉพาะฟิลด์ของตัวเองใน __slots__ — ฟิลด์ที่สืบทอดมาจะหายไปเงียบ ๆ ยังไม่มีคลาสไหนในโปรเจกต์เป็นแบบนั้น แต่ตระกูล *State กับ *Info คือรูปที่ชวนให้มีคลาสแม่ในอนาคตพอดี

และ None ต้องผ่านไปเป็น null จริง ไม่ใช่ str(None) ที่ได้ตัวอักษรสี่ตัวว่า "None" — ซึ่งจะแยกไม่ออกจาก edge ที่ชื่อ None จริง ๆ และทำให้ทุกการตรวจสอบผลรวมนับมันเป็นค่าที่ระบุได้
