# M1b — Metrics

**Status:** proposed
**Supersedes `ST-D22`. Registers `ST-D24` .. `ST-D33`.**
**Prior art:** `docs/specs/2026-08-23-m1a-canonical-state.md` §12 (what M1a hands here),
`research/CADENCE_ARCHITECTURE_CONTROLLER_CONTRACT.md` §17-§18.

---

# 1. What M1b is for

The roadmap's terminal claim (M9) is that a network-aware controller beats Max-Pressure
under oversaturation and spillback. Every milestone from M3 onward ends in the same act:
**comparing two controllers and defending the number**.

Nothing can do that today. M1a produces a run directory; there is no way to turn one into a
number, and no way to say two numbers may be put in the same table.

> **M1b turns a run directory into numbers that survive a comparison — including under the
> regimes the project exists to study, where the naive versions of those numbers invert.**

`DIRECTION` §2's M1b row names the mechanism ("derived metrics"); this is the purpose the
mechanism serves, and §4's scope is derived from it.

## 1.1 The inversion this milestone must be immune to

Under regime C, mean travel time over completed trips is not noisy — it is **backwards**:

| | trips completed | mean travel time, completed | still in network at horizon |
|---|---|---|---|
| Controller A | 300 | 60 s | 200 |
| Controller B | 480 | 90 s | 20 |

A wins the headline while stranding 200 vehicles. The metric rewards starving the trips that
would have been slow. This is survivor bias; in regimes C and D it is the normal condition,
not an edge case.

`--tripinfo-output.write-unfinished` was added at M1a to make the stranded trips visible.
**It is necessary and not sufficient**, which §5 takes up: it restores the tail's *presence*
and not its *magnitude*.

# 2. Principles

Each rules something concrete out. Where a principle only restates an existing rule it is
marked as such rather than counted as new.

**`ST-D24` — Metrics are computed offline, from the run directory alone.**
Settled at M1a §3.2 by measurement: a whole S0 run is 28 KB and an M8 corridor hour is
single-digit megabytes. Consequence: a new metric, or a `_v2` of an existing one, re-scores
every historical run without re-simulating. Rules out computing metrics during the run,
which would make one definition change cost a full experiment matrix.

**`ST-D25` — Every metric declares its population, not only its unit.**
`CLAUDE.md` §4 already requires temporal scope in the name; this extends it to *who is
counted*. "Mean waiting time" is not a metric. "Mean waiting time per completed trip" and
"per departed vehicle" are different numbers that can pick different winners. Rules out any
metric whose denominator is implicit.

**`ST-D26` — Every vehicle is accounted for, and the accounting has two axes.**
Outcome and incidence are orthogonal; §3 defines both. Rules out a completion rate that
divides by the wrong total, and the §1.1 inversion.

**`ST-D27` — A censored quantity is never averaged with an uncensored one.**
An unfinished trip's duration is not its travel time; it is how long the clock ran. Pooling
the two populations reintroduces the §1.1 inversion through a different door. Rules out the
most natural reading of "trip metrics over completed and unfinished trips" — a pooled mean.

**`ST-D28` — A quantity whose unit already includes accumulated time is never
time-integrated.**
Measured, §5.2: summing `waiting_total_now_s` across steps overstates total waiting by 16×,
while summing `halting_count_veh` over the same steps agrees with `tripinfo` to 1%. Both are
levels that decay, so decay is not the test — the unit is. `_now_s` integrated over seconds
yields veh·s², which is not a waiting time. `CLAUDE.md` §4's unit suffix already carries the
answer. Rules out integrating any `_s` quantity, and rules *in* `Σ halting_count_veh · Δt`,
which is the standard total-delay metric and exactly the `waiting_total_episode_s` shape §4
holds up as correct.

**`ST-D29` — A metric whose support does not exist in the run declares it, and a metric
with no honest definition is deferred rather than approximated.**
The mechanism is a `limitations` field on the registry entry, non-empty wherever §3.3's
unnamed bucket could have belonged in a denominator, with a test asserting it. Rules out
both the confident number with no basis and the plausible approximation that reads as fact —
§5.3 is this principle choosing deferral over approximation.

**`ST-D33` — Comparability and reproducibility are different questions over different
field sets.** Reproducibility asks whether two runs are the same run; comparability asks
whether two may share a table, under which the controller *must* differ and the seed usually
does. Rules out `verify-run` reusing `reproducible_fields()`, which would refuse the M3
comparison §7 names as its first consumer.

**`ST-D32` — The run records the fleet.** Vehicle types with length and minimum gap. Rules
out deferring a *writer* change to the milestone that consumes it — the same rule §8 applies
to the cross-tab, applied consistently. See §5.3.

**Not new, restated for completeness.** A metric definition is immutable and only `_v2`
supersedes it (`CLAUDE.md` §4).

# 3. Vehicle accounting (`ST-D26`)

A metric that loses vehicles produces a defensible-looking number about a subset nobody
named. The partition below is what every population-scoped metric (`ST-D25`) selects from.

## 3.1 Outcome — exactly one per vehicle

| bucket | how it is recognised | `s0_turning_oversaturated/v1` |
|---|---|---|
| **completed** | a `tripinfo` row with `arrival >= 0` | 183 |
| **in network at horizon** | a `tripinfo` row with `arrival = -1` | 178 |
| **never inserted** | counted, never named — see §3.3 | 349 |

Reconciled exactly against `state/network.parquet` at the horizon:

```
departed_total_veh 361 = arrived_total_veh 183 + active_veh 178
tripinfo rows      361 = departed_total_veh
rows arrival = -1  178 = active_veh
departed 361 + pending_insertion 349 = 710 = departures due in [0, 180)
```

Every figure in §3 and §5 was re-measured against the committed fixture once it existed.
The first draft quoted a scratch variant built during review, which the fixture deliberately
is not — it scales the asymmetric demand rather than flattening it (§10.2). Those numbers
are gone rather than annotated: a document a dispatched agent is told to read cannot carry
a figure that is one fixture out of date.

An unfinished row carries `arrival="-1.00"` and an empty `arrivalLane`. Not every one carries
`vaporized="end"` — so `vaporized` is not the filter.
The population filter is `arrival >= 0`, declared, not inferred from a null check.

**This identity holds only while no vehicle is removed rather than arriving.**
`--collision.action remove` and `--time-to-teleport.remove` both break it. Neither is set
today, but both rest on unpinned SUMO defaults, which `build_sumo_command`'s own docstring
says is the thing it exists to prevent — so M1b pins them. A metric asserting the identity
fails loudly if it stops holding rather than absorbing the difference.

Verified at every one of the fixture's 180 steps, not only at the horizon, and it holds
while 13 teleports are in flight.

`--max-depart-delay` is a third way a vehicle can leave without arriving. Its default of -1
disables it, and it is pinned alongside the other two for the same reason.

## 3.2 Incidence — orthogonal, zero or more per vehicle

**Teleport is not an outcome bucket.** SUMO relocates a stuck vehicle and it continues its
route, so a teleported vehicle normally *completes*. `teleport_total_veh` counts
`TELEPORT_STARTED` events, so one vehicle teleporting twice contributes two. It is an
incidence count, not a vehicle count, and a metric that treats it as a bucket produces a
total exceeding the demand.

Teleport is reported as: incidences, distinct vehicles affected, and the completion rate of
affected versus unaffected vehicles. A teleport is a control failure the simulator papered
over; the metric layer un-papers it.

Measured on the fixture, whose `time_to_teleport_s` is 30: 13 teleports across 13 distinct
vehicles, of which 11 completed (85%) against 172 of 348 unaffected (49%). Teleported
vehicles complete at a *higher* rate than unaffected ones, because being teleported is what
released them — which is the clearest possible demonstration that this cannot be an outcome
bucket.

## 3.3 The bucket with no identity

The 349 never-inserted vehicles have no row anywhere in the run directory. They are a count
in `state/network.parquet` and nothing else, so no per-vehicle question — how long each
waited to be inserted, which origin-destination pair was starved — can be answered.

**M1b does not add them.** It reports the count, declares the limitation on every metric
whose denominator could reasonably have included them, and hands the question forward (§9).
Under regime C this bucket is larger than either other bucket, so a completion rate over
*departed* and one over *due* are different claims and both are worth stating.

# 4. Scope

## 4.1 In

| | Why |
|---|---|
| Registry mechanism: a declaration beside each function, and a test asserting emitted columns and declared metrics are the same set in both directions | `CLAUDE.md` §4 and §7 make the registry a contract; the test makes it mechanical rather than aspirational |
| Trip metrics, over the outcome buckets of §3.1, never pooled across the censoring boundary | §1.1, `ST-D27` |
| Queue metrics per lane, including `queue_length_m` as back-of-queue distance | The primary observable of signal control; §5.3 |
| The fleet record — `topology/vehicle_type.parquet` (`ST-D32`) | A writer change; deferring it falsifies `ST-D19` for every run made before M8 |
| Network metrics — throughput, completion rate on both denominators, still-in-network, pending insertion | `ST-D26` |
| Teleport incidence, per §3.2 | `ST-D26` |
| `cadence metrics <run_dir>` writing `metrics/` into the run directory | `ST-D24` |
| `cadence verify-run <a> <b>` | §7 |
| `distinct_veh` on the ground-truth cross-tab, and the reconciliation test it enables | §8 |
| The read boundary for the metrics package | §6, and `ST-D23` requires the answer here |

## 4.2 Out

| | Owner |
|---|---|
| Turn-ratio estimation, shared-lane queue attribution, the starvation guard, the residual-bias limitation | **M8**, whose Max-Pressure controller is the first consumer. §9.1 records the roadmap amendment this required |
| `available_storage_ratio`, `storage_capacity_veh` as *metrics* | **M8**, which needs them for downstream storage and runs the congested scenarios their estimate has support on. The *data* they need is recorded here (`ST-D32`), so no run has to be repeated |
| Spillback, junction blocking, gridlock indicators | **M8**, per `DIRECTION` §2 |
| Controller latency, solver timeout | **M2**. No controller exists to time |
| Cross-run aggregation and plots | **M6**. M1b's contribution is that aggregation becomes a groupby over a stable schema with comparability already checkable |

## 4.3 The line between M1b and M6

M1b makes one run defensible and makes comparability checkable. M6 aggregates across runs
and seeds. The hard part — semantics that do not shift, and knowing when two numbers may
share a table — is M1b's; the arithmetic on top is M6's.

# 5. What measurement changed

Each of these was found by running an oversaturated variant of `s0_turning` (all twelve
flows at `period=3.0`, `end_s=180`) through the real pipeline, not by reasoning.

## 5.1 `write-unfinished` restores presence, not magnitude (`ST-D27`)

| | count | mean duration | mean waitingTime | mean timeLoss |
|---|---|---|---|---|
| completed | 183 | 77.93 s | 34.94 s | 48.00 s |
| unfinished | 178 | 77.76 s | 55.44 s | 67.68 s |

The unfinished trips are unambiguously the worse ones — 59% more waiting, 41% more time loss.
**Their mean durations are identical to two decimal places.** That is the whole argument in
one line: `duration` for an unfinished trip is **right-censored at the horizon**, so it
measures how long the clock ran and not how long the trip took. Pooling the two populations
produces a number that cannot see the difference between them, and a controller that strands
more vehicles moves that number in its own favour.

M1b therefore reports the two populations separately and never averages across the boundary.
Where a single headline number is wanted, it is throughput or completion rate — quantities
censoring does not distort — not a mean duration.

## 5.2 Summing a stock overstates by 16× (`ST-D28`)

```
sum over steps of state/lane.parquet waiting_total_now_s : 177,886 s   10.9x
sum over steps of state/lane.parquet halting_count_veh   :  16,093     1.0% low
sum of tripinfo waitingTime over all 361 rows            :  16,263 s
```

`waiting_total_now_s` comes from `lane.getWaitingTime()`, which is the sum over resident
vehicles of each one's *accumulated consecutive* wait — a level that decays as a queue
discharges, not an increment that accrues.

The middle row is why the rule is about units and not about decay. `halting_count_veh` is
also a level that decays, and integrating it lands within 1% of the trip-side total. The
difference is that `waiting_total_now_s` already carries seconds: integrating it over seconds
yields veh·s², which is not a waiting time at all.

Total waiting therefore comes from `tripinfo` (a per-trip flow), and `waiting_total_now_s` is
used only for instantaneous and peak statistics — never integrated. The registry entry for
every quantity states which kind it is.

## 5.3 The run directory carries vehicle length but not gap (`ST-D32`, `ST-D29`)

Vehicle length is recoverable from data already recorded:
`occupancy_ratio × length_m / vehicle_count_veh` returns exactly 5.0 m on 1,947 of 2,391
non-empty samples on `s0_turning`, and 5.0 m on 2,015 of 2,442 on the oversaturated fixture
— the fleet's car length. SUMO's occupancy counts vehicle length only.

`minGap` is not recoverable this way and appears nowhere else: the vType in `demand.rou.xml`
does not set it (SUMO's 2.5 m default applies), `topology/lane.parquet` carries only
geometry and speed, and the manifest carries `demand_sha256` rather than content.

**The first draft of this section deferred both candidate answers — recording the fleet, and
estimating jam spacing from jammed lanes — to M8. That was wrong, by the rule §8 states one
page later.** One of the two is a writer change and one is an estimator. §8's rule assigns
them: the estimator can wait, the writer change cannot. Deferring the fleet record leaves
every run between now and M8 unable to answer an M8 question without being re-simulated,
which is exactly what adopted `ST-D19` promises cannot happen.

So M1b records the fleet. `binding.vehicletype` exposes `getIDList`, `getLength`,
`getMinGap` and `getMaxSpeed`; `topology/vehicle_type.parquet` carries
`(type_id, length_m, min_gap_m, max_speed_mps)`, read once at connection time alongside the
rest of the topology. It is a handful of rows.

**`queue_length_m` is then defined honestly, as back-of-queue distance:**

```
queue_length_m = halting_count_veh × (length_m + min_gap_m)
```

The first draft defined it as the road the halting vehicles *occupy* — length only, no gap —
because that was computable without the fleet. Measured on the oversaturated fixture, that
definition reports a full lane as two-thirds empty:

| `left0A0_0`, length 189.6 m, peak 25 halting | |
|---|---|
| occupy-definition | 25 × 5.0 = **125.0 m**, 66% of the lane |
| back-of-queue | 25 × 7.5 = **187.5 m**, the lane is full |

That is the failure `CLAUDE.md` §4 exists to prevent: a plausible number saying a third of
the lane is free at the moment it is spilling back. A registry entry saying "occupy" rather
than "span" does not protect a reader who compares 125 against 189.6. The occupy definition
is also degenerate on a single-vType fleet — a unit conversion of a count, carrying nothing
the count does not — and not computable at all on the mixed fleet `PD-Q01` puts in scope,
since occupancy covers resident vehicles rather than the halting subset.

The mixed-fleet weighting is declared as a `limitations` entry (`ST-D29`) until a
mixed-fleet scenario exists to test it against.

**What stays deferred is not the same deferral.** `storage_capacity_veh` and
`available_storage_ratio` are *metrics*, not data. Their denominator wants jam spacing under
real congestion, and M8 both needs them and runs the scenarios where the estimate has
support — the oversaturated fixture §10 adds already bounds `minGap` to [2.29, 2.58] against
SUMO's true 2.5, so the support exists the moment M8 wants it. Recording the fleet now means
M8 computes them over every run made in between.

# 6. The metrics package, and what it is allowed to read (`ST-D23`)

`ST-D23` records that the run directory's privilege split fences code and not data:
`state/traversal.parquet` plus `evaluation/tripinfo.parquet` reconstruct 89% of the
privileged cross-tab's vehicle-steps. It says the question belongs to the first offline
loader, "before that code exists, not after."

**`src/cadence/metrics/` is that first loader, so M1b answers it.**

## 6.1 The answer (`ST-D30`)

The metrics package reads `manifest.json`, `topology/`, `state/` and `evaluation/`. **It
does not read `ground_truth/`**, and an architecture test asserts the string does not appear
in the package — the same exact-set mechanism that fences the simulation side.

This is a rule about *this package*, not a claim that the partition is airtight. It is not:
the reconstruction in `ST-D23` remains possible for anything that opens the directory.

What the rule buys is narrow, and worth stating exactly rather than overselling:
`ground_truth/` cannot enter the metrics package through the front door, and extending the
allowlist to reach it is a deliberate edit that an existing architecture test already forces.
It does **not** buy oracle detection from a metric's declared inputs. A metric reconstructing
turn intent from `state/traversal.parquet` and `evaluation/tripinfo.parquet` — the 89%
reconstruction `ST-D23` names — declares only unprivileged inputs and is indistinguishable
from an honest one. The declaration reveals directory provenance, not oracle provenance, and
that gap stays open in §9.2.

An oracle metric is a legitimate research instrument. When one is wanted it goes in a
separate package with its own allowlist entry and a name that says so. `ST-D30` is the
*decision* never to extend the allowlist to `metrics/`; the enforcement already exists.

## 6.2 Registry entry

`ARCH §18` requires name, version, definition, units, input fields, aggregation, thresholds.
Two are added and one is honest about being empty:

- `population` — which outcome bucket of §3.1, required by `ST-D25`
- `quantity_kind` — `stock` or `flow`, required by `ST-D28`
- `limitations` — what this metric cannot tell you. Required non-empty wherever §3.3's
  unnamed bucket could have belonged in the denominator (`ST-D29`)
- `config_dependencies` — the values that change the number without changing the definition.
  **Empty on every M1b entry, and the reason is structural rather than incidental.**
  `CLAUDE.md` §4 pushes interpretation into the name and the version, which leaves this field
  almost nothing: `queue_p95` and `queue_p90` are two metrics, not one metric with a setting,
  and the halting threshold lives inside SUMO's `getLastStepHaltingNumber` identically for
  every run, so it can never discriminate two of them. The one genuine case M1a §12 envisaged
  — the turn-ratio window length and prior weight, tuned rather than named — moved to M8 in
  §4.2. The field is declared so M8 needs no schema change, and `verify-run` is scoped to the
  manifest half until then.
- `thresholds` — null on every M1b entry. Thresholds arrive with spillback and gridlock at
  M8. The field is declared so M8 does not need a schema change; that it is empty is stated
  rather than hidden.

The declaration lives beside the function that computes the metric. A registry in a separate
file drifts from the code, and the drift is silent; the same-set test in §4.1 is what makes
`CLAUDE.md` §7's registry requirement mechanical.

# 7. `cadence verify-run` (`ST-D33`)

Two runs are comparable when scenario, demand, code, platform and simulator agree. The
manifest carries all of it.

**It must not reuse `reproducible_fields()`.** That set answers a different question — *are
these the same run?* — and excludes only the two timestamps, so it still contains
`controller_id`, `controller_version`, `seed`, and four run outcomes (`terminal_time_s`,
`step_count`, `unmatched_traversal_count`, `termination_reason`). Every one of those differs
by construction in the comparison this command exists to bless. Applied as written in the
first draft, `verify-run` would have refused M3's fixed-time-versus-actuated comparison —
the very case §7 names as its first consumer. `ST-D33` records the distinction so a later
reader does not merge the two sets back together.

Comparability is its own frozen set:

```
scenario_id  scenario_version
network_sha256  demand_sha256  config_sha256
begin_s  end_s  step_length_s  time_to_teleport_s
cadence_commit  platform_tag  sumo_version  binding
```

`controller_id`, `controller_version` and `seed` are reported as the *intended* differences
rather than compared for equality — a comparison with nothing differing there is a
reproducibility check, not a controller comparison, and `verify-run` says which it is
looking at. It refuses outright when either run carries a `cadence_dirty_digest`, per M1a
§9.2.

**Its first consumer is M3, not M6.** `DIRECTION` §2 makes M3 "tuned fixed-time vs SUMO
actuated — the acceptance test for M2", which is a two-run comparison. This was nearly
deferred on the belief that studies begin at M6; the M3 row is the refutation.

# 8. The cross-tab schema change (`ST-D31`, superseding `ST-D22`)

`ST-D22` says the cross-tab's per-lane turn split is unverified and that "M1b must verify it
before validating anything against it". §4.2 moves the estimator to M8, which would leave
that decision's meaning changed by a scope table — which `CLAUDE.md` §6 forbids. `ST-D31`
supersedes it, and splits the deadline in two.

**The estimator can wait. The schema cannot.**

`ground_truth/lane_turn.parquet` is written by every run from now until M8. Making the
schema change at M8 leaves every earlier run permanently unreconcilable, which directly
contradicts `ST-D24`'s promise that a new metric re-scores historical runs.

So M1b makes the *writer* change and lands the reconciliation test; M8 builds the estimator
that consumes it:

1. `Traversal` gains `from_lane_id`. The detector already holds it, it is observable, and it
   makes the join exact for all 315 rather than the 306 whose `connection_id` resolves.
2. `GroundTruthReader` accumulates the distinct vehicles seen per `(lane, next_edge)` and
   emits `ground_truth/lane_turn_vehicle.parquet` at the end of the run.
3. A test asserts `distinct_veh(L,E) >= traversals(L→E)` for every pair. Every vehicle that
   crossed from lane L to edge E must have stood on L intending E; the excess is vehicles
   that changed lane before the stop line.

A permutation confined to one lane's own movements swaps `distinct_veh` and leaves
`traversals` alone, so the inequality breaks on one side. **This must be verified by
mutating the extractor and watching the test fail** — if it does not fail, the design is
wrong and the finding is reported rather than worked around. Measured: 7 of 16 traversed
pairs.

**What it catches, and what it does not.** The inequality is one-sided, so it can only fire
where the swap pushes `distinct_veh` below a traversal count it must dominate — formally,
where `d(E1) < t(E2)` or `d(E2) < t(E1)`. Slack from lane-changing is what it must overcome
first, and on this network that slack runs 0 to 19 vehicles. A swap confined to a lane whose
slack exceeds its movement imbalance survives: `top0A0_1` is such a lane, and permuting it
alone produces zero violations. Seven of eight approach lanes are covered; that one is not.

Being one-sided also means nothing bounds `distinct_veh` from above, so a reader that
over-attributes — crediting every vehicle to every edge its lane serves — passes untouched.
That one is cheap to close and is closed: the test pins the non-null pair count at 24, which
over-attribution collapses to 16.

Closing the first properly needs a two-sided bound, which needs per-vehicle identity in the
cross-tab. That is a larger schema question and it belongs with M8's estimator, which is the
first thing whose correctness depends on the distinction.

# 9. What M1b hands forward

## 9.1 The roadmap amendment this specification required

`DIRECTION` §2's M1b row named queue attribution, `turn_ratio_sliding_window_v1`, the
starvation guard, the residual-bias limitation, and the derived lane quantities. §4.2 moves
the first four to M8 and §5.3 moves two of the three lane quantities with them.

That is a roadmap change, and it is made in `DIRECTION` §2 and in `ST-D31`, not implied by a
scope table here. The engineering case is that nothing in M2's safety layer or M3's two
baselines consumes a turn ratio or a movement-queue split; `ARCH §7`'s Max-Pressure adapter
is the first thing that does.

**The cost, stated rather than buried:** `ST-D15` pulled the movement layer into M1a
specifically so turn ratios could be estimated, and M1a §14.1 called a movement layer with no
consumer "Critical — decorative". This amendment leaves it decorative until M8. That is
accepted: a layer waiting for its consumer is a smaller problem than an estimator built five
milestones before anything reads it.

## 9.2 Questions M1b does not answer

1. **Per-vehicle identity for the never-inserted bucket** (§3.3). Under regime C it is the
   largest bucket, and insertion delay is a real control outcome. Recording it needs a source
   the run directory does not have.
2. **Jam spacing** (§5.3), and with it `storage_capacity_veh` and `available_storage_ratio`.
   M8 needs them for downstream storage; M8 also runs congested scenarios, which is where the
   observational estimate has support.
3. **Whether the privilege partition should exist as three directories or two** (`ST-D23`).
   §6.1 binds the metrics package; it does not resolve the partition itself, and the 89%
   reconstruction from unprivileged directories stays unfenced.
4. **Three `ARCH §17` items with no home yet.** "Residual / cycle failure" and "network
   progress" need a cycle boundary the run directory does not mark, which arrives with M2's
   phase control. "Teleport reason" has no source at all: `state/teleport.parquet` records
   `kind` and not why. Named here rather than left silent, per `CLAUDE.md` §6.

# 10. Testing

| Kind | What | Fixture |
|---|---|---|
| **Registry** | emitted columns and declared metrics are the same set, both directions; every entry has a non-empty `population`, `quantity_kind` and — where §3.3's bucket applies — `limitations` | none |
| **Unit** | each metric against a hand-built frame with a known answer | none |
| **Agreement** | §10.1 — two independent measurements of one quantity | both |
| **Property** | a completion rate is in [0, 1]; a censored population never enters a mean with an uncensored one, asserted structurally through the declared population | none |
| **Architecture** | the metrics package does not name `ground_truth` (`ST-D30`); it imports nothing from `simulation/sumo/` | none |
| **Accounting** | §3.1's identity at every step, not only the horizon, and failing loudly rather than absorbing a difference | both |
| **Teleport** | §3.2's incidence axis, and that a teleported vehicle can complete | oversaturated |
| **Reconciliation** | §8's inequality, verified by mutation | **`s0_turning`** |
| **Integration** | `cadence metrics` on a real run directory; `verify-run` accepts two runs differing only in controller, and refuses two differing in a comparability field | both |

## 10.1 The agreement tests, and why they are the important row

Every finding in §5 came from the same method: measure one quantity two independent ways and
look at the gap. No other method in this table would have found any of them. A unit test
against a hand-built frame is written by whoever wrote the metric, so it catches
transcription errors, not definition errors — it distinguishes "runs" from "crashes", never
"runs" from "correct".

Four two-source identities exist in the run directory today, and each closes a real class:

```
Σ_t halting_count_veh · Δt   ≈  Σ tripinfo waitingTime     measured 16,093 vs 16,263, 1.0%
tripinfo rows with arrival>=0 == arrived_total_veh at the horizon
tripinfo row count            == departed_total_veh at the horizon
per-movement traversal totals ≈  tripinfo route counts
```

The first is the one that would have caught the 10.9× error behind `ST-D28`, which a
`quantity_kind`-is-non-empty assertion would not.

## 10.2 The second fixture

`s0_turning` drains, so it exercises none of §1.1, §5.1 or §5.2 — every measurement in §5
came from an oversaturated variant that does not exist in the repository. M1b adds it.

Three properties are load-bearing and were each established by measurement:

**It keeps the asymmetry** — for a reason that survived, and by a margin that did not.
The demand is scaled rather than flattened because flattening destroys the property
`tools/build_s0_scenario.py`'s own comment says it exists for: "a movement-mapping error
cannot hide behind symmetry". That argument stands on its own.

The quantitative case does not. Re-measured against §8's permutation on the committed
fixtures, counting only pairs a traversal reaches — the 8 pre-positioning pairs have zero
traversals, so `distinct_veh >= 0` holds there by construction and they can never fail:

| fixture | pairs violating §8's inequality after the within-lane permutation |
|---|---|
| `s0_turning`, asymmetric, drains | **7 / 16** |
| `s0_turning_oversaturated`, asymmetric, scaled | **3 / 16** |

A scratch flattened variant scored the same 3 during review, so **scaling bought none of the
3.3× the first draft attributed to it**. What separates 7 from 3 is saturation, not symmetry:
congestion inflates `distinct_veh` relative to traversals, and slack is what the inequality
spends before it can fail. §8's reconciliation therefore runs on `s0_turning`, and the reason
is congestion rather than the reason first recorded.

Baseline violations are zero on both, so the inequality itself is sound.

**It teleports.** Inheriting `time_to_teleport_s: 300.0` against a 180 s horizon makes a
teleport structurally impossible, which would ship §3.2 and every teleport metric untested
against the code path whose own GOTCHA says regimes C and D are where it matters. At 30 s the
fixture produces 13 teleports across 13 distinct vehicles.

**Its name says what it is.** `DIRECTION` §4 holds that regimes are "parameterised variants
of a scenario, not separate projects" (`TC-D01`), and `ScenarioConfig` has no regime
dimension — so a new scenario id is the only mechanism available today, and that is a gap
worth naming rather than papering over. The id keeps the network's defining property:
`s0_turning_oversaturated/v1`, not `s0_oversaturated/v1`.

`tools/build_s0_scenario.py` currently hardcodes each scenario's root, departure window and
period table as module constants. Generating a third from it requires parameterising that,
which is in scope here.
